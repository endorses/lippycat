# v0.11 Phase 1 production-regression baseline

**Captured:** 2026-09-02

**Code:** `dda4064bf1baeda06870e7b8edcc2d268d04246b` plus the Phase 1 benchmark harness

**Host:** Linux 6.18.32-2-lts, amd64, Intel Core i9-13900HX

**Toolchain:** Go 1.26.3, `GOMAXPROCS=1`

These are pre-fix measurements. They are review evidence for the regressions,
not portable wall-clock acceptance thresholds. Each runtime value below is the
median of three one-second benchmark runs on an otherwise non-isolated
developer workstation.

increase from 1,000 to 100,000 entries reproduces the full-map eviction scan.

## RTP call lookup allocations

Allocation results are captured with the separate
`BenchmarkGetCallIDForRTPPacketAllocations` family, rather than inferred from
runtime. This distinction matters because the allocation *count* remains
mostly constant while the allocated bytes grow with the materialized active-call
slice.

Command:

```bash
GOMAXPROCS=1 GOCACHE=/tmp/lippycat-go-cache go test -tags all \
  ./internal/pkg/tui -run '^$' \
  -bench '^BenchmarkGetCallIDForRTPPacketAllocations$' -benchmem -count=1
```

| Active calls | Destination hit | Source hit | Miss |
|---:|---:|---:|---:|
| 10 | 2,400 B, 8 allocs | 2,400 B, 8 allocs | 2,440 B, 10 allocs |
| 1,000 | 229,474 B, 8 allocs | 229,474 B, 8 allocs | 229,530 B, 12 allocs |
| 5,000 | 1,130,608 B, 8 allocs | 1,130,608 B, 8 allocs | 1,130,656 B, 12 allocs |

Endpoint-key formatting contributes fixed allocations. The cardinality-scaled
bytes are the stronger evidence of eager active-call slice materialization and
must be compared separately in the after-fix run.

## Reproduction notes

- The benchmark harness pre-fills each bounded detector map, triggers its
  one-time cap warning outside timing, and then performs sustained new-key
  insertion while the map remains at capacity.
- RTP fixtures register one unique endpoint per active call and verify the
  expected hit or miss before timing.
- Future before/after comparison should use the same host, toolchain,
  `GOMAXPROCS`, benchmark duration, and count. CPU frequency was not pinned, so
  multiple-run distributions should be retained rather than comparing a single
  minimum.
